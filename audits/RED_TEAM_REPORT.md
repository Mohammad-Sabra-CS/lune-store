# Executive Summary

Red-team review (SUB-AGENT 10, final) of the proposed LUNE rebuild architecture **as amended** by the Phase C conditions (SECURITY, PERFORMANCE, SCALABILITY) and Phase D corrections (UX, DESIGN, RESPONSIVE). Every load-bearing claim in the nine reports was spot-checked against the actual code; the 20 mandated failure-mode questions are answered one-by-one with file evidence in Findings §B.

**Verdict: the amended architecture is APPROVED WITH CORRECTIONS.** The Phase A reports are accurate at a rate I have rarely seen — of ~40 claims spot-checked, all material ones reproduce in code. The consolidated plan (WP0–WP11 + T1–T9 rulings + Phase C/D conditions) resolves every confirmed defect and introduces no structural mistake. However:

1. **One unresolved head-on contradiction survives between two Phase C reviews**: SCALE condition C1 *requires* an idempotency pre-check SELECT ("read-check = required fast path… both are required"), while PERF condition C2 *bans* it ("not a SELECT-then-INSERT pre-check") and re-derives the checkout round-trip budget (3 vs 4) from that ban. Both were issued as binding conditions on the same WP2 pipeline and nobody reconciled them. Ruling below (Findings §C-1): **SCALE wins on correctness; the budget line must read "≤ 4 DB round trips flat".**
2. **One Phase D condition is incomplete as written**: DESIGN X2's "WP8-lite" P0 slice claims the light-surface focus-ring WCAG failure is closed by a one-line `--ring` token change — but the checkout form hardcodes `focus-visible:border-gold focus-visible:ring-gold/40` on its light inputs (`checkout-form.tsx:113-114`), bypassing the token. 3. **One Phase C condition pair is internally in tension**: PERF C1a permits admin-session validation "memoized per lambda instance for its TTL" while SEC C-1.1 requires server-side revocation — a revoked session would stay live on every warm instance until TTL. Cap the memo at seconds or drop it.
4. **Five smaller findings all nine agents missed** (Findings §D): the DB-path `decrementStock` reports only the *first* sold-out slug (undermining the planned itemized sold-out feedback); an email-throw would trigger `restoreStock` on an order that exists; flipping delivered→new nulls `deliveredAt` (history loss beyond DATA's re-click finding); JS-off users can see everything and buy nothing (never stated explicitly); and the `expectedTotal` check has a sale-boundary clock-skew false-positive.

## §B — The 20 questions, answered

1. **What can break?** In order of real-world likelihood: (a) duplicate orders from double-submit/second-tab (QA-02/03 — confirmed: no ref guard, no idempotency, no storage listener); (b) admin sign-out silently not working (QA-01 — confirmed cookie-path mismatch); (c) denial-of-inventory via scripted COD orders (SEC F-1 — confirmed: zero throttling on `placeOrder`, `DEFAULT_STOCK` 50 falls to ~3–10 requests); (d) silent stock loss when order-insert fails after decrement and compensation also fails (`products.ts:282-284` swallows); (e) customer charged a total they never saw after an admin price change (QA-04); (f) receipt HTML injection the day `RESEND_API_KEY` lands (SEC F-7); (g) DB outage with a cold/invalidated cache takes down every storefront page, because the locale layout awaits `getStoreProducts()` (`layout.tsx:79`) — QA-20(d) flagged the 404 case; the general case is accepted-but-unmitigated in Phase B (see §D-7). All of (a)–(f) are resolved by WP1–WP4 as amended.
2. **10,000 simultaneous visitors?** Absorbed. Home/shop/product/checkout are SSG (`generateStaticParams`, PERF build table); product data sits behind `unstable_cache` tag `"products"` — zero runtime DB on cache hit (verified: the only storefront DB path is the layout's cached read). neon-http is stateless fetch-per-query — no pool to exhaust. Worst case is one cache regeneration per successful order (each `placeOrder` calls `revalidateTag`, `checkout/actions.ts:108`), which is a trivial SELECT rate even at tens of orders/minute. SCALE's 10k assessment stands. The genuine spike risks are self-inflicted: over-tight WAF thresholds under Jordanian carrier NAT (SCALE's warning, carried into T3), and the 3.9 MB video × 10k visitors ≈ 39 GB bandwidth (WP7's re-encode is also a cost fix).
3. **Many simultaneous checkouts?** No oversell: per-item conditional `UPDATE … WHERE stock >= qty` (`products.ts:231-237`) is atomic per row; concurrent last-unit buyers race to fast, correct `soldOut`. No connection exhaustion. What *does* happen today: concurrent duplicate submissions of the same cart create N orders and N decrements. Fixed by WP2 **only under SCALE C1's pipeline** — see §C-1.
4. **Database slow?** Checkout degrades linearly: ~5+ sequential HTTPS round trips (seed INSERT ×2, SELECT, N UPDATEs, INSERT — `checkout/actions.ts:65-106` via `products.ts`), each paying the slow DB; no statement timeouts are configured anywhere. Admin (`force-dynamic`, full-table reads) suffers directly. Storefront is insulated on cache hit; a slow DB only delays background regeneration (stale-while-revalidate keeps serving). WP2's seed-once + single-statement decrement cuts the checkout multiplier to ~3–4 round trips.
5. **An API fails?** Resend: structurally cannot fail an order (`receipt.ts:145-172` never throws — verified; and without the key it only logs). Vercel Blob: upload wrapped in try/catch, admin sees "Upload failed" (`admin/products/actions.ts:184-187`). Neon mid-checkout: caught, `restoreStock` best-effort, customer gets generic `server` error — the documented compensation window (accepted under T1 + SCALE C5 drift stat). One coupling no report stated — see §D-2.
6. **An image fails?** Product images are `next/image fill` over `bg-night`/solid backgrounds with alt text (RESP inventory — confirmed); a failed image leaves a dark block, no layout collapse. Hero: the marble still owns LCP; the video is decorative and only crossfades in on `playing`, so a failed video fetch is invisible (`hero-media.tsx`). Blob-hosted admin images are constrained by `remotePatterns` (`next.config.ts:19-24`). Acceptable; no action beyond WP7.
7. **Slow mobile connection?** First visit pays ~290 KB gz JS + 9 preloaded fonts (460 KB, both scripts — confirmed no `preload:false` in layout) + 80 KB HTML; the 3.9 MB video is deferred to idle but still fetched on data plans (no `saveData`/reduced-motion gate — QA-12). Content is visible by 2.5 s even if JS stalls (`reveal-fallback`, `globals.css`). WP7 (font split, video re-encode + gate, favicon) is the fix and PERF O1's pull-forward of WP7 is endorsed — it has zero dependencies on WP5/WP6.
8. **JavaScript fails?** Content: fine — the no-JS CSS fallback force-reveals at 2.5 s. Commerce: **dead**. Add-to-cart is client state; checkout submits via `onSubmit` + `startTransition` (`checkout-form.tsx:81-111`) with `noValidate` — there is no `action=` progressive-enhancement path, so no JS = no possible purchase. This is a defensible consequence of the localStorage-cart architecture, but **no report ever states it** (see §D-5). Record it as an accepted trade-off in CLAUDE.md rather than discovering it in an incident.
9. **Can a customer manipulate the price?** No. The action accepts only `{slug, qty}` per item; price, sale, delivery fee, and total are recomputed from `getStoreProductsFresh()` server-side (`checkout/actions.ts:64-81`); `paymentMethod` is `z.literal("cod")`; qty is server-clamped 1–20, ≤10 items, re-checked against live stock. Confirmed by direct read. Residual business-rule bypass: duplicate slugs evade the per-item cap (QA-10 — confirmed, priced correctly, up to 200 units/slug) — WP2's unique-slug refine closes it. The new `expectedTotal` (WP2) must stay UX-only per SEC C-2.3 — the plan already says so.
10. **Can a customer access admin functionality?** Not without the cookie: every admin page and every mutating action independently re-checks `isAdminAuthenticated()` (verified at all 5 pages + all 5 actions). Weaknesses are in the *token*, not the gate: static password-derived value (offline-crackable if leaked, non-revocable), no login throttling, and broken logout (QA-01). WP1 + SEC C-1.1…C-1.4 resolve this fully. One nuance in §D-3 (session memoization vs revocation).
11. **Unnecessary requests?** Yes, all confirmed: the seed INSERT on every uncached product read (twice per checkout); the awaited Resend call in the checkout response path; ~230 KB of wrong-script font preloads per locale; a 3.9 MB single-play video; a 71 KB favicon. WP2/WP4/WP7 eliminate every one.
12. **Unnecessary database queries?** Yes: `ensureSeeded` (above); `listOrders()` full-table SELECT (with JSONB items) to render 5 dashboard rows (`admin/page.tsx` + `orders.ts:63-68`); `listFeedback()` unbounded likewise. WP2 (seed-once) + WP5 (indexes, dashboard LIMIT per SCALE) + deferred SQL filters are the right-sized answer.
13. **Unnecessary dependencies?** One: `shadcn` (a CLI) in runtime `dependencies` (`package.json:25`, imported nowhere — ARCH verified, I confirm the dep entry). `drizzle-kit`'s esbuild advisory is dev-only (SEC F-4). Everything else is used. WP6 covers both.
14. **Can caching return stale or incorrect data?** Stale-briefly by design: tag invalidation is SWR, so one visitor may see pre-update stock/price (accepted, correct trade-off). Incorrect: no — sale windows are evaluated client-side at view time (`effectivePrice(product, now)`), so cached pages can't show expired sales, and all money paths use uncached `getStoreProductsFresh()` (verified). The two guarded risks: any *future* admin mutation that forgets `revalidateTag` (PERF's regression note), and the WP6 `use cache`/Cache Components migration silently changing route staticness — PERF C4's CI route-table precondition is the right gate and must be treated as blocking.
15. **Can two users create conflicting orders?** Only in the benign direction: the conditional decrement serializes on Postgres row locks; the loser gets `soldOut` and their cart self-prunes on `router.refresh()` (`checkout-form.tsx:103-106`, `cart-context.tsx:74-83`). No oversell state exists. Confirmed.
16. **Can duplicate orders be created?** Today, yes — three ways: double-submit before the `isPending` re-render (QA-02), a second tab's stale cart (QA-03 — no storage listener, confirmed), and a network-level replay of a lost response (SCALE F3, the most likely real-world case). The amended WP2 fixes all three **if and only if** the SCALE-C1 pipeline is the one implemented (pre-check + constraint + conflict-loser-restores + key regeneration per SCALE C4) — see §C-1 for the surviving contradiction.
17. **Can the same button be clicked multiple times?** Checkout submit: yes, within one render frame (no synchronous ref guard — confirmed). Add to cart: rapid second click silently swallowed for 1.4 s (QA-14). Cart steppers: clamp silently at limit (QA-13). Admin "Mark delivered": re-click resets the archive clock (`orders.ts:74` unconditionally sets `deliveredAt = new Date()`) and delivered→new *nulls* it (§D-4); double-cancel in the future flow is guarded only if SEC C-5.1/SCALE C6's transition-guard-before-restore ordering is followed. All covered by WP2/WP5 + QA fixes, with §D-4's addition.
18. **Does Arabic RTL break anything?** Yes, four confirmed classes: synthetic italic on Arabic poetry (no `font-style` reset anywhere in `globals.css` — QA-07); heavy inline tracking fracturing joined script at ~15 sites (RESP R-1); the sheet close button hardcoded English + physical `right-3` colliding with the RTL drawer title (`ui/sheet.tsx:68`); locale switch dropping the query string so the order number vanishes from `/ar/confirmation` (QA-06). Foundations (logical properties, `[dir="rtl"]` type compensation, per-locale drawer side, LTR phone/email inputs) are genuinely solid. WP8/WP9 as corrected by Phase D (A-5 decoupled from the T6 owner decision; opt-in `.label-caps` over the blanket selector — DESIGN's self-correction is right, the blanket `[class*="tracking-"]` selector would have stripped Latin product names) cover all of it.

## §C — Challenges to the amended architecture (Phase C/D conditions that are wrong or unreconciled)

**C-1 (the one surviving contradiction) — SCALE C1 vs PERF C2 on the idempotency pre-check.** SCALE (Phase C, WP2 condition C1, blocking): the pipeline must be *pre-check SELECT by key → atomic decrement → `INSERT … ON CONFLICT` → conflict-loser restores*, and "the read-check … is a required fast path". PERF (Phase C, condition C2): the key "must be enforced via the UNIQUE constraint itself … **not** a SELECT-then-INSERT pre-check, which would add a round trip to every order", and tightens the CI budget to "≤ 3 flat" on that basis. These are mutually exclusive instructions for the same WP2 code, both labeled conditions, never reconciled anywhere. **Ruling: adopt SCALE C1.** Without the pre-check, every replay performs a real decrement that must then be *un-done* via the same best-effort `restoreStock` the whole plan is trying to retire — a replay under load with a failed restore silently loses stock, which is precisely SCALE F2's defect reintroduced through the new mechanism. The pre-check costs one indexed primary-key-adjacent SELECT (~10–30 ms) per checkout on a COD flow where 300–800 ms of email latency is simultaneously being removed; correctness beats the round trip. Consequences: the WP11 CI budget line must read **"≤ 4 DB round trips per checkout regardless of cart size"** (SCALE's arithmetic), not PERF's "≤ 3 flat"; PERF C2 is downgraded from condition to preference. SEC C-2.2's payload-hash-on-replay applies to the pre-check path identically.

**C-2 — DESIGN X2's "WP8-lite" scope is insufficient for its own goal.** The condition claims the focus-ring WCAG 1.4.11 failure is closed by flipping light-mode `--ring`/`--sidebar-ring` to `#7c6132` in `globals.css`. But the checkout form — the highest-stakes light-surface form on the site — overrides the token at the call site: `inputClass = "… focus-visible:border-gold focus-visible:ring-gold/40"` (`checkout-form.tsx:113-114`), i.e. gold at 2.18:1 (worse with `/40` ring opacity) survives the token fix untouched. RESP's re-audit instruction ("grep `text-gold[^-]`") also misses it — this is `border-gold`/`ring-gold`, not `text-gold`. **Amendment: WP8-lite must additionally grep `(ring|border)-gold` on light-surface components and fix `checkout-form.tsx` inline (→ `focus-visible:border-gold-deep focus-visible:ring-gold-deep/40` in current token names).** No other Phase C/D condition is affected.

**C-3 — PERF C1a vs SEC C-1.1: session-memo undermines revocation.** PERF permits admin-session validation "optionally memoized per lambda instance for its TTL"; SEC requires server-side revocation and server-enforced expiry. Memoizing validity for the session TTL (12 h) means a revoked/rotated session stays authenticated on every warm Fluid instance until TTL — revocation becomes cosmetic. **Amendment: memo lifetime ≤ ~30–60 s, or no memo (one indexed lookup per admin request is already accepted by PERF's own verdict).** Low stakes (single-admin store) but the conditions as written contradict each other's intent.

**C-4 — T1/C5 drift-stat vs PERF C3a — compatible, but pin it.** SCALE C5 demands the drift-detection query ship *in WP2*; PERF C3a forbids "a standing query on every dashboard view". Both are satisfiable (compute on the orders page or behind an explicit refresh button) — but WP2's implementer should be told explicitly, since satisfying SCALE naively (a dashboard stat card) violates PERF. Not a contradiction; a specification note.

**C-5 — Everything else holds.** I attacked the remaining rulings and conditions and found no further fault: T2 (SSG confirmation, no lookup ever) survives an IDOR/staticness/truthfulness cross-exam; T3/C-3.1-3.2's WAF-with-committed-fallback is the only rate-limit shape that works under carrier NAT (and C-3.2's `Next-Action` targeting note is technically correct — server actions POST to page URLs); T4/C-3.3-3.5 is implementable exactly as specified (the current upload code already uses the required path shape — evidence above); T5 (no proxy pre-filter) is right — `proxy.ts:12`'s matcher exclusion is load-bearing for i18n; T7's alias layer is verified as non-blocking for every functional fix; SCALE's CTE warning for the gateway milestone is accurate Postgres semantics (data-modifying CTE side effects commit regardless of the gating branch); Phase D's WP9a promotion, A-5 decoupling, V-1 move, WP8→WP9 ordering, WP10a/b split, and 320px matrix are all endorsed without amendment.

## §D — Missed by all nine agents (new findings)

**D-1 — DB-path `decrementStock` reports only the FIRST sold-out slug; the dev path reports all.** `products.ts:238-240` returns `{ ok: false, soldOut: [item.slug] }` on the first failed conditional UPDATE, while the dev-JSON branch (`:247-252`) computes the complete list. QA-15's fix and Phase B's "itemized soldOut feedback" (WP2/§3 cart line) assume the server "already computes" the full list — in production it does not. When WP2's single-statement decrement lands, derive the full shortfall from the `RETURNING` diff (`items.filter(i => !returnedSlugs.has(i.slug))`) so prod and dev behave identically. Severity: Low (wrong-but-plausible messaging), but it would have silently shipped a prod/dev behavioral fork inside a P0 work package.

**D-2 — An email throw would restore stock under a real order.** `await sendReceiptEmail(orderInput)` sits inside the same try/catch as `createOrder` (`checkout/actions.ts:105-114`); if the email module ever threw (the invariant is currently upheld, but it is one refactor away), the catch would run `restoreStock` even though the order row exists → inventory inflated by the order's qty *and* the customer sees "server" error and re-submits a duplicate. No report states this coupling; SEC's WP4 note ("never-throws must survive the `after()` move") is adjacent but not this. The WP4 `after()` migration structurally eliminates it — one more reason WP4 is correctly P0 — and WP11 should pin a regression test: *a throwing email sender must neither fail the checkout result nor touch stock*.

**D-3 — `updateOrderStatus` nulls `deliveredAt` on delivered→new.** `orders.ts:74`: `deliveredAt = status === "delivered" ? new Date() : null`. DATA F4 caught the re-click reset; nobody caught that un-delivering (a one-click accident in the admin table) *erases* the delivery timestamp entirely, destroying archive history with no confirmation. WP5's set-once `deliveredAt` fixes the reset but, as specified ("set only when NULL"), would make re-delivering after an accidental un-deliver a no-op with a *stale* date. The legal-transition work (SEC C-5.2) must define delivered→new explicitly: either forbid it or specify the `deliveredAt` semantics. Related: `setOrderStatus(id, status)` has no runtime enum validation — an authenticated admin client can POST any string into `status` (typed only at compile time), and with no DB CHECK until WP5 it lands in the table and breaks `filterOrders`/`isArchived` string comparisons. One-line zod enum in WP1's `AdminActionState` work.

**D-4 — No-JS commerce is impossible, and no report says so.** Detailed under question 8. Content degrades gracefully (the reveal-fallback is genuinely good); purchasing does not exist without JS — no `<form action>` fallback anywhere in the funnel. **D-5 — `expectedTotal` has a sale-boundary clock-skew false positive.** WP2's equality check compares a client-computed total (client clock via `effectivePrice(product, now)`) against a server-computed one (server clock). Correct behavior (the server total is truthful) — but WP11's suite should include the boundary case so the UX copy for "priceChanged" is exercised, and the check must compare *totals*, not per-item prices, to avoid multiplying the window.

**D-6 — DB-down + invalidated cache = full storefront outage (partially noted, unowned).** QA-20(d) noted the 404-page case only. The locale layout's `getStoreProducts()` (`layout.tsx:79`) is the single point every storefront route flows through; `unstable_cache` cannot serve stale-on-error across a failed regeneration after a tag bust. Right-sized answer given the frozen static/DB split: on regeneration failure, fall back to `staticProducts` seed defaults (identity + `PACKAGE_PRICE` + `DEFAULT_STOCK`) so the storefront renders while checkout (fresh path) correctly fails. Priority: Low (Neon SLA is high; SSG pages keep serving until invalidated) — but it costs ~10 lines in WP6.
